Why the tables in the other guides look out of order. They follow the order the beats appear in your script, not the numbers. Your script delivers the guarantee at beat 18 before the results at beat 14, because she says it as part of the story: “I only bought it because of the 30 day money back promise.” That is deliberate and it is one of the reasons the ad works, so the number order and the reading order are not the same thing.

Same count, completely different beats. Only two overlap: 1 and 19, the hook and the close, because those always follow whatever changed. Everything else is separate, which is what makes the two tests independent.

How to read it

  1. Beat 10 is the tell. It is the only row where the three moves genuinely separate. If the mechanism moved, you changed the angle. If it did not, you did not, whatever you called it.
  2. Beat 1 always moves. In all three. The hook is built out of whatever changed, so it can never stay still.
  3. Beats 2, 3, 13, 18 and 14 never move. The narrator, how it started, the product, the guarantee and the results. That is the spine.
  4. Count the changes to name the test. One beat is an iteration. Six is a new scene. Eight is a new argument. If you set out to change the angle and three beats moved, the angle did not really change.

The order you run them

  1. Prove something with an iteration. Cheapest test you will ever run.
  2. Widen it with use case swaps. This is where volume comes from.
  3. Keep going until three to five scenes work. That is scaling. Build the dedicated landing page, then raise budget.
  4. Run the winners in another bucket. UGC, then VSL. Exhaustion is per bucket, not per angle.
  5. Only then reach for an angle swap, when the argument itself stops producing.

You are between 2 and 3. One angle, five scenes mapped, two of them live.
